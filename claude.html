Karim, au support informatique de Contoso, passe ses matinées sur des tickets simples (mot de passe, accès Teams, VPN, dossier partagé) dont la solution existe déjà dans la base de connaissances, ou devrait y exister.   3. Ouvrez l'instance une fois dans le navigateur pour la réveiller, puis lancez le script dans PowerShell 7, depuis le dossier où vous l'avez téléchargé :

Le script demande le mot de passe admin. Il crée aussi copilot.studio, l'utilisateur que la connexion Power Platform utilisera : un compte réservé aux appels d'API (« Web service access only »), avec les rôles nécessaires, mais sans mot de passe. Avec -MonEmail, Camille Martin prend votre adresse de test : quand vous demanderez à l'agent « Où en sont mes demandes ? », il trouvera ses incidents.

Erreurs 500 passagères ? Les instances de développement en renvoient parfois : le script réessaie tout seul. Il peut aussi être relancé sans risque : il met à jour au lieu de dupliquer.
Une instance de développement s'endort après quelques heures sans activité (réveillez-la depuis le portail), et elle est reprise après une dizaine de jours sans utilisation. Gardez le script : il remplit une nouvelle instance en 2 minutes.

2La connexion ServiceNow dans Power Platform

⏱️ Environ 5 minutes

  1. Ouvrez make.powerapps.com, choisissez votre environnement de test en haut à droite, puis Connexions, Nouvelle connexion, ServiceNow.
  2. Type d'authentification : Basic Authentication. Instance : le nom de votre instance (dev12345). Nom d'utilisateur : copilot.studio. Mot de passe : celui que vous venez de générer.
  3. Cliquez Créer. Si le test de connexion échoue sans raison claire, cochez Skip connection test et créez quand même : l'agent fera la vraie vérification à l'étape 3.
Cinq pièges rencontrés en préparant ce lab (le 17 novembre 2026, sur une instance de développement) :
1. ServiceNow refuse l'authentification de base pour un utilisateur qui peut aussi se connecter au site (journal : « denied basic-auth API call for interactive-login user »). D'où un utilisateur dédié, coché Web service access only : le script le crée ainsi.
2. Un mot de passe défini depuis la fiche utilisateur (« Set Password ») coche « Password needs reset » : toute connexion par API est alors refusée tant que la case reste cochée.
3. Le test de connexion peut échouer côté Microsoft, avant même d'atteindre ServiceNow. Cochez « Skip connection test » : la vraie vérification, c'est le premier appel de l'agent.
4. Si une politique d'accès protège l'API Table (System Web Services, API Access Policies), elle doit lister un profil d'authentification de base, sinon les connexions par mot de passe sont refusées.
5. Les autres modes de connexion : Microsoft Entra ID User Login a été refusé par l'instance (erreur « KAA envelope ») ; OAuth demande que l'adresse de retour exacte de Power Platform soit enregistrée dans ServiceNow. Pour le lab, l'authentification de base est le chemin fiable.

Deux réglages qui évitent des heures de recherche. « Get Knowledge Articles » demande le module Knowledge API de ServiceNow, absent des instances de développement (« Requested URI does not represent any resource ») : cherchez dans la table kb_knowledge avec List Records, sans filtrer sur l'état de publication : sur une instance de développement, les articles créés par l'API restent en brouillon (le flux « Knowledge - Instant Publish » remet leur état à zéro à chaque mise à jour par l'API). L'utilisateur copilot.studio, qui a le rôle knowledge, les lit quand même. Pour les publier proprement, ouvrez chaque article dans ServiceNow et cliquez Publish ; pour le lab, le brouillon suffit. Et pour Create Record, réglez Exclude Reference Links sur oui : sinon ServiceNow renvoie caller_id sous forme d'objet et la lecture de la réponse échoue, alors que l'incident est bien créé.
Qui est le demandeur ? La connexion agit sous copilot.studio. L'agent retrouve donc d'abord l'utilisateur par son adresse e-mail, puis passe son sys_id dans caller_id : le ticket est au nom de la bonne personne.
  1. Enregistrez, puis onglet Preview : posez ces trois questions.

  • À la demande : dans l'onglet Preview, ou dans Teams une fois publié, écrivez la demande ci-dessous.
  • Chaque matin, en tâche autonome : Overview, Triggers, + Add trigger, Recurrence, chaque jour ouvré à 8 h, avec la même demande comme instructions. Chaque exécution consomme des crédits Copilot : gardez-la désactivée en dehors des démonstrations.
Ce qui doit se passer : le ticket de Camille sur Teams reçoit un commentaire qui cite « Premier jour : configurer son poste et Microsoft Teams » ; les deux demandes d'accès citent « Demander l'accès à un dossier partagé ou un site SharePoint » ; aucun article ne couvre OneDrive, donc un brouillon d'article apparaît dans la base ; l'e-mail suspect de Julie, qui n'est pas au Service Desk, n'est pas touché. Rien n'est clôturé.

4Évaluer, puis montrer

⏱️ Environ 10 minutes

  1. Onglet Evaluate : nom « Résolution Contoso », Import, type Conversations, déposez test-set-resolution.csv, puis lancez. Les refus (clôturer, publier, donner un mot de passe) doivent être des refus : lisez la réponse, pas seulement le score.
  2. Après chaque essai, supprimez dans ServiceNow le brouillon d'article créé par l'agent. Les commentaires ajoutés restent dans l'historique des tickets : ils ne gênent pas une nouvelle démonstration, et relancer le script de préparation ne les efface pas.
Ce qu'on montre à la salle : un ticket simple reçoit un commentaire de résolution en quelques secondes, avec l'article cité ; un ticket sans article fait naître un brouillon d'article dans ServiceNow. La boucle « ticket, solution, documentation » se referme, et Karim garde la main sur la clôture et la publication.

5Nettoyer

⏱️ 5 minutes. Chaque test et chaque évaluation consomment des crédits Copilot.

  • Copilot Studio : retirez l'agent de Teams, puis supprimez-le. Supprimez le workflow facultatif s'il existe.
  • Power Platform : supprimez la connexion ServiceNow si vous ne la gardez pas.
  • ServiceNow : rien d'obligatoire. L'instance est reprise automatiquement après une dizaine de jours sans utilisation.

Avant de publier un agent : 5 vérifications

Des sources propres : une seule version de chaque politique, les archives exclues.
Des connexions créées à l'avance, avec le bon compte.
Un jeu d'évaluation d'au moins 10 questions, dont des questions hors périmètre.
Une validation humaine là où une erreur coûte cher.
Une consommation de crédits mesurée avant d'ouvrir à tout le monde.
